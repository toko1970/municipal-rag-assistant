# 差分レビュー

**適用対象:** 実装後、PR前、ユーザーがレビューを求めた場合。

## 見る順序

1. `git status`と差分を把握し、依頼に不要なファイルが混ざっていないことを確認する。
2. 対象パスのルール、根拠となる要件・計画・schema、既存設計と評価規約を照合する。
3. 変更のentry pointからデータが保存・検索・回答・分類されるまでを追う。正しいコードだけでなく失敗経路、再実行、旧データ、境界値を確認する。
4. 対応するtestと実行結果を確認し、未実行・外部依存・検証範囲を区別して報告する。

## 観点と優先度

- correctness: 回答根拠、分類・保留条件、期限計算、版・施行日、状態遷移。
- data/security: 秘密情報、権限、migration、データ消失・重複、外部入力。
- retrieval/evaluation: 指標やsplitの意味、gold漏洩、規約version、評価結果の再現性。
- testing/operations: 回帰の不足、弱いtest、API費用、retry、障害時の整合性。
- design: 既存責務、schema契約、`design/`・`eval/`資料との整合。

- **P0:** 秘密漏えい、データ破壊、重大な誤回答・誤分類、採用gateの迂回。解決するまで受け入れない。
- **P1:** 高い確率で発生する不具合、重要な回帰・test欠落、仕様・評価契約との不整合。根拠ある対応か明示的裁定が必要。
- **P2:** 低リスクの改善・読みやすさ。判断理由を添えて残せる。

PR作成前に、実装担当とは別セッションのAIによる差分レビューを最低1回行う。実装経緯で誘導せず、差分と必要な仕様だけを渡す。設計・契約との整合は`.codex/agents/design_reviewer.toml`、境界値・異常系は`.codex/agents/edge_case_reviewer.toml`を使い、変更リスクに応じて観点を選ぶ。P0は必ず解消し、P1は修正または根拠ある明示的な裁定を記録してから進む。レビューagentの指示はsandbox権限を制限しないため、親セッションの権限範囲内で使う。利用可能な環境で独立レビューが実施できない場合は、未実施のままレビュー済みと扱わず、その制約を人間へ報告する。レビューで仕様矛盾や正解不明が見つかった場合、推測で決着させず人間に報告する。

PR本文を作る場合は課題、解決、テスト、レビューしてほしい点を示す。外部サービスへの投稿は人間の承認後に行う。
