# RAG品質評価と採用判定

**適用対象:** `eval/**`、回答品質・汎化評価の設計、候補比較、評価実行、結果報告。

## 評価開始前

1. `eval/GENERALIZATION_VALIDATION_PLAN.md`、`eval/INTERVENTION_ADOPTION_PROTOCOL.md`、`eval/reports/README.md`、関連する最新checkpointと既存runを読む。
2. 今回の目的、評価対象、対象外、使うset、run上限・費用、合格条件を先に明記する。実行はユーザーの依頼範囲と利用可能なAPI/予算に従う。
3. 開発用・回帰用・holdout用の区別を維持する。`*.sealed/`等のgold custodian管理データを開いたり、質問やgoldを候補調整へ混ぜたりしない。公開manifestのhash・開封手順に従う。
4. 回答契約・分類規約の版を明記する。過去の正解規約と新しい規約、検証済み結果と未実施計画を混同しない。

## 候補比較と実行

- 候補間で質問set、データ、model、検索設定、budget、retry、評価コードを揃え、変更する因子を限定する。
- 指標だけでなく母数、区分別内訳、重大誤り、費用・latency、失敗条件を記録する。推定・proxy・人手判定を区別する。
- candidate選択後に評価条件を変更しない。変更が必要なら別runとして理由を残す。
- run前に費用とprovider制限を確認し、有限の実行にする。結果artifactは既存の命名・保存方式を使い、上書きや既存の結果改変を避ける。

## 採否

- 既存の採用判定プロトコルと個別gateに従う。全体平均の改善だけで、区分別悪化・重大誤り・回帰を隠さない。
- 合格条件未達、未実施、データ不足は明示する。閾値・gold・splitを候補に都合よく変更しない。
- 採用結論は根拠となるrun、コード・設定のcommit、使用setと規約版へ結び付ける。根拠が足りなければ「未判定」とする。
