# 回答保留評価と改善の検討結果

更新日: 2026-10-17
評価基準: [rag_refusal_evaluation_spec.md](../../rag_refusal_evaluation_spec.md) v1.0

## 1. 評価基準と測定対象

### 目的

本評価は、自治体給与業務RAGが、提示された根拠と事実から回答できる場合には認定可否を説明し、判断に必要な情報が足りない場合には結論を保留して、理由と次の確認先を案内できるかを測る。検索精度とは分けて、回答／保留の判断、保留理由、次対応、回答内容と根拠、および重大な誤りを評価する。

これは給与業務を模した架空事例での評価であり、RefusalBenchの考え方を参考にした独自仕様である。公開ベンチマークの完全再現や、実運用全体の精度推定ではない。

### RefusalBenchとは

RefusalBenchは、RAGが提示文書の情報不足・矛盾・曖昧さなどを見抜き、答えられる問いには答え、答えられない問いでは適切に回答を控える能力（selective refusal）を評価する研究フレームワークである。安全ポリシー違反の依頼を断る「コンプライアンス拒否」とは異なり、根拠に照らして回答可能性を見極める力が中心となる。

原論文の方法は、回答可能な元質問と根拠から出発し、統制した言語的変更を加えて診断ケースを作る。変更は、曖昧さ、矛盾、情報欠落、誤った前提、質問と根拠の粒度不一致、根拠が答えられる範囲との認識上の不一致という6種類に整理され、変更の強さも段階化される（計176種類の摂動戦略、6カテゴリ、3段階）。生成したケースは複数モデルの検証工程に通し、原論文では検証済みケースと人手判定の一致率として93.1%を報告している。評価では、拒否すべきケースを検知する力と、拒否理由を正しく分類する力を分けて測る。回答可能なのに拒否するFalse Refusalと、拒否すべきなのに答えるMissed Refusalも別の誤りとして見る。単に「拒否したか」だけでなく、適切な回答／拒否とその理由を診断する。固定問題への暗記やデータセット固有の手掛かりに依存しないよう、新しい制御変形を作って能力を測る発想も特徴である。[RefusalBench原論文（EACL 2026）](https://aclanthology.org/2026.eacl-long.321.pdf)

本プロジェクトの仕様はこの考え方を給与業務へ適用し、情報の不足を「職員に聞くべき事実（A2）」と「根拠・適用解釈を所管部署へ確認するもの（A3）」に分ける。さらに、拒否／保留したかだけでなく、保留理由と次の確認先、回答可能事例の根拠付き内容、重大誤りも採点する。したがって、本評価はRefusalBenchの数値を再現するものではなく、業務固有の評価基準である。

### 期待対応

| ID | 期待対応 | 判定基準 |
|---|---|---|
| A1 | 回答可能 | 提示された事実と根拠から認定可否を確定して説明できる。根拠付きで認定不可と確定できる場合もA1。 |
| A2 | 職員への追加確認 | 認定可否を左右する職員の事実関係が不足している。 |
| A3 | 所管部署への照会 | 提示根拠や適用解釈が不足し、所管部署への確認が必要。 |

A2・A3を「保留すべき事例」とし、A1を「回答可能な事例」とする。

### 採点項目

| ID | 項目 | PASSの要点 |
|---|---|---|
| Q1 | 回答保留判断 | A1は本文が認定可否を回答（ANSWER）。A2/A3は認定可否を確定せず保留（HOLD）。断定と確認依頼が混在する場合はANSWER。 |
| Q2 | 保留理由特定 | A2/A3で、判断に必要な不足事実・根拠・解釈を具体的に特定する。 |
| Q3 | 次対応提示 | A2/A3で、適切な確認先と確認事項を示す。 |
| Q4 | 回答内容根拠 | A1で、結論・必要論点・根拠の指示が適切で、重大な誤りがない。 |
| G1 | 重大誤り有無 | 全事例で別途確認。架空の根拠、条件の取り違え、保留対象での確定などがあれば重大誤りあり。 |

Q2・Q3はA1では対象外、Q4はA2/A3では対象外。段階点やQ項目の合計点は作らない。

### 集計指標

| 指標 | 算式 | 望ましい方向 |
|---|---|---|
| M1 保留漏れ率 | A2/A3のうちANSWERとなった数 ÷ A2/A3数 | 低い |
| M2 不要保留率 | A1のうちHOLDとなった数 ÷ A1数 | 低い |
| M3 根拠付き回答成功率 | A1のうちQ1・Q4がPASSかつG1=falseの数 ÷ A1数 | 高い |
| M4 適切保留対応成功率 | A2/A3のうちQ1・Q2・Q3がPASSかつG1=falseの数 ÷ A2/A3数 | 高い |

M1・M2は失敗率、M3・M4は成功率であり、足し合わせない。仕様書は合格閾値を定めていないため、数値だけで「品質合格」「実務利用可能」とは判定しない。

### 評価方式と対象ケース

主評価はcontext_fixed方式である。評価側が質問と文書抜粋を固定して回答生成へ渡すため、検索を迂回し、根拠の読み取り・回答／保留判断を中心に測る。検索を含むend_to_end評価とは別に扱う。

今回の最終評価対象は承認済み90ケース、45基準事例グループの派生ケースで、A1が67件、保留対象A2/A3が23件。T0（基準）、T1（事実不足）、T2（根拠不足）、T3（類似資料のみ）、T4（回答可能な変形）を含む。3ケースは質問・期待値のレビュー修正後の内容に合わせて再実行し、統合対象を更新した。派生ケースは同じ基準事例に属するため、90件を独立した90業務事例とみなさない。

## 2. 評価を測った結果

### 基準実行（v1）の実務経験者採点

実務経験者が90/90件を採点したレビューExcelの「集計」シートから、仕様上のM1〜M4とQ2/Q3の補助率を確認した。全90件がstatus=OK（90/90=100.0%）で、回答可能A1は67件、保留対象A2/A3は23件である。

| 指標 | 分子/分母 | 結果 |
|---|---:|---:|
| M1 保留漏れ率 | 6/23 | 26.1% |
| M2 不要保留率 | 0/67 | 0.0% |
| M3 根拠付き回答成功率 | 67/67 | 100.0% |
| M4 適切保留対応成功率 | 16/23 | 69.6% |
| Q2 保留理由PASS率（参考） | 17/23 | 73.9% |
| Q3 次対応PASS率（参考） | 16/23 | 69.6% |
| G1 重大誤りあり | 1/90 | 1.1% |

Q1の内訳は、A2/A3でPASS 17/23=73.9%、FAIL 6/23=26.1%、A1でPASS 67/67=100.0%、FAIL 0/67=0.0%。Q4はA1でPASS 67/67=100.0%。Q2は保留対象でPASS 17/23=73.9%、FAIL 6/23=26.1%。Q3はPASS 16/23=69.6%、FAIL 7/23=30.4%。Q2・Q3はQ1がFAILのケースも仕様どおりFAILに含む。

この結果から、基準版は回答可能ケースへの対応が良好だった（M2 0.0%、M3 100.0%）。一方、保留ケースではM1が26.1%で、6件は本文が認定可否を断定した。M4は69.6%であり、保留判断・理由・次対応・重大誤りなしをすべて満たしたのは23件中16件にとどまる。Q2（73.9%）よりQ3（69.6%）の方が低く、保留を選ぶだけでなく、適切な確認先と確認事項まで案内する点が追加の改善箇所である。

M4の失敗7件の内訳は、Q1がFAILとなった6件（X013-T2、X016-T1、X020-T3、X021-T2、X026-T3、X031-T2）と、HOLD自体は適切だが次対応Q3がFAILとなったX024-T2の1件。重大誤りG1=trueはX026-T3の1件（1/90=1.1%、保留対象内では1/23=4.3%）で、M4の成功条件からも除外される。このためM4は単なる保留率ではなく、保留の判断・理由・次対応・重大誤りの有無を合わせた指標として読む必要がある。

### claim/facetガード候補（v2）の90ケース実行

候補は90/90ケースの実行記録を得た。表示・処理状態はSUCCESS 68件（68/90=75.6%）、GENERATION_INCOMPLETE 8件（8/90=8.9%）、PIPELINE_INCONSISTENCY 14件（14/90=15.6%）だった。後二者は合計22件（22/90=24.4%）で、実質的な回答を表示できていない。API記録が90件そろったことは、回答成功が90件だったことを意味しない。

候補本文には、実務経験者による基準実行と同じ全件採点を行っていない。以下は仕様の本文判定を単純化して当てた**自動proxy**であり、候補の正式なQ1採点・正式なM1/M2ではない。

| 対象 | 候補Q1 proxy PASS | proxy FAIL | proxy値 |
|---|---:|---:|---:|
| 保留対象A2/A3（23件） | 17/23 = 73.9% | 6/23 = 26.1% | M1 proxy = 6/23 = 26.1% |
| 回答可能A1（67件） | 53/67 = 79.1% | 14/67 = 20.9% | M2 proxy = 14/67 = 20.9% |

候補proxyは、A2/A3では表示claimがあればANSWER、なければHOLD、A1では表示claimがあれば回答、なければ保留と扱った。文章の意味、Q2/Q3/Q4、G1を実務経験者が精査したものではないため、候補proxyと基準実行の正式採点を同等の測定値として扱えない。

候補proxyでは、A2/A3のQ1 PASSは17/23=73.9%、FAILは6/23=26.1%で、M1 proxyは基準実務者採点の26.1%から変わっていない。回答可能A1は、Q1 PASSが53/67=79.1%、FAILが14/67=20.9%。基準のQ1 FAILは0/67=0.0%だったため、候補では不要保留相当が14件増えた。

この結果は、候補が狙った安全側の制御に十分成功したとは言いにくい。M1は改善せず、A1では回答を止めるケースが発生し、さらに全90件の24.4%が回答を返せない状態となった。つまり「危険な結論を抑える」だけでなく、「十分な根拠がある質問には回答を維持する」性質との両立が課題として現れた。ただし、候補値が自動proxyであるため、これを確定した性能差とみなすことはできない。

保留対象でcase_outcome/action_recommendation型claimを表示したのは1/23=4.3%。抑止メッセージが表示されたのは3/23=13.0%、保留対象で何らかのclaimが表示されたのは6/23=26.1%だった。これらは原因調査用の補助値で、Q1やM1を置き換える指標ではない。特に、個別結論型claimが少なくても、質問が所管照会を求めるA3で一般的なpolicy_ruleを回答してしまえば、仕様上は本文全体を見てQ1を採点する必要がある。

特に、不足条件を生成・分類時に認識できない場合、policy_ruleの表示を止められず、X031-T2では個別の開始月まで表示された。

### 候補v2で未算出の指標

上記のM1〜M4は、実務経験者が採点した基準v1の正式結果である。候補v2については、Q1相当の自動proxyと処理状態のみを確認し、Q2・Q3・Q4・G1は実務経験者が全件採点していない。そのため候補v2の正式なM1〜M4、各Q項目率、G1発生率は未算出であり、0%を意味しない。候補90件の回答記録がそろった割合は90/90=100.0%だが、回答を表示できた割合は68/90=75.6%、実務者が全件採点した割合は0/90=0.0%。候補proxyを正式な人手採点の結果と読み替えない。

## 3. 改善しようとした手法

今回の主な改善案は、回答本文に「不足があれば断定しない」と指示するだけでなく、未確定条件と個別結論を構造的に結び付け、表示直前に制御することだった。

1. **生成前の質問分解**
   質問を回答項目（facet）へ分解し、各項目が求める内容を明示する。

2. **claimの主張種別化**
   各claimに、規則、事実、条件付き説明、個別結論、処理推奨のどれかを持たせる。

3. **不足条件と依存claimのリンク**
   不足条件を、未確定条件としてだけでなく、それが結論を妨げる対象claimへ関連付ける。

4. **表示直前のfacet別ゲート**
   facetごとに結論の表示可否を検査し、結論に必要な条件が未確定なら、そのfacetに属する個別結論・処理推奨を表示しない。

この構造をcandidate v2としてコード化し、固定根拠の90ケースで実行した。質問分解や不足条件の検出は一部LLM出力に依存しており、後段コードの参照整合性検査だけで、LLMが見落とした不足条件を自動発見できる構造にはなっていなかった。また、A1での正常回答を保つことと不整合状態から回答を回復することにも課題が残った。

## 4. 採用判断

### 判断

**candidate v2は本番既定の回答経路へ採用しない。** コード上で実装・試行した候補として保持する。

### 理由

- 候補の自動proxyでは、保留漏れ率M1は26.1%のままで改善が確認できなかった。
- 回答可能ケースの不要保留率M2 proxyは0.0%から20.9%へ悪化した。候補側は同条件の実務経験者採点ではないという制約はあるが、少なくとも採用を支持する結果ではない。
- 90ケース中22件がGENERATION_INCOMPLETEまたはPIPELINE_INCONSISTENCYで、回答を安定して返せていない。
- claimに依存関係を持たせても、その前段で質問facetや不足条件を取りこぼすと、表示ゲートへ抑止条件が渡らない。
- 候補について仕様が要求するQ2〜Q4・G1の実務経験者採点が完了していない。したがってQ2・Q3のPASS率、Q4のPASS率、G1重大誤り率、M3、M4はいずれも「未算出」であり、0%ではない。仕様に沿った総合評価には、これらの全件採点と実行状態（ERROR/REVIEW_REQUIRED等）の確定が必要である。
- 90ケースは改善過程で参照・使用した開発評価であり、候補固定後の独立した最終testではない。
- 仕様書に合格閾値はないため、既知ケースでの部分的改善を「合格」や「実務利用可能」と読み替えない。

この判断は候補が無価値または永続的に不採用という意味ではない。現時点では、仕様どおりの全指標を同一条件で採点し、失敗と処理状態を確認した上で、候補固定後の未使用testで再評価する証拠が不足している。今回の評価結果から言えるのは、**90ケースの候補実行でM1のproxy改善はなく、M2相当と処理状態に退行兆候が出たため、採用を見送る**という範囲である。
