# Phase 2: End-to-End評価と汎化確認

## 目的

検索だけでなく、回答生成、根拠支持、回答分類、表示まで通して制度問い合わせに正しく答えられるかを評価した。このフェーズの精度は、全条件を満たした**総合回答成功率**で表す。

## 1. 開発用130問の改善

改善前の失敗13件を原因別に分けると、回答生成6件、回答分類4件、検索3件だった。最大件数の回答生成から着手したが、広いprompt変更は対象改善0/4、control退行4/6だったため小規模pilotで停止した。

次に、原因が揃っていた複数文書検索へ限定し、Query Decomposition、生成前版注記、版競合時だけ動くVersion Resolverを組み合わせた。

| 指標 | 改善前 | 採用構成 | 差 |
|---|---:|---:|---:|
| 総合回答成功 | 117/130 (90.0%) | 120/130 (92.3%) | +3 |
| 回答生成失敗 | 6 | 6 | 0 |
| 回答分類失敗 | 4 | 3 | -1 |
| 検索失敗 | 3 | 1 | -2 |

改善は3件、退行は0件だった。各変更は独立ではなく、検索で新旧根拠を揃え、版注記とResolverで適用版を決めて初めて成功した質問がある。このため各手法の改善率を単純加算していない。

詳細: [精度改善の意思決定レポート](../ACCURACY_IMPROVEMENT_DECISION_REPORT.md)

## 2. Sealed text holdout

開発中に使わなかった50シナリオ・100表現へ候補を適用し、予測を固定してからgoldを開封した。

| 指標 | 結果 |
|---|---:|
| 総合回答成功 | 83/100 (83.0%) |
| Scenario stability | 39/50 (78.0%) |
| 回答分類 | 86/100 |
| 回答内容 | 94/100 |
| Document retrieval | 100/100 |
| Evidence retrieval | 100/100 |

検索は全件成功した一方、最大の失敗原因は回答分類14件だった。開発評価120/130との差は質問集合が異なるため、単純な9.3ポイントの退行とは扱わない。未知の複数文書・版境界で、過度に`判断要`へ寄せる傾向と具体期限の計算不足が見つかった。

詳細: [Text sealed holdout受入評価](../TEXT_HOLDOUT_ACCEPTANCE_RESULTS.md)

## 3. Holdout後の対象限定改善

具体的な起算日から期限日を求める質問だけを、決定的なPython計算へrouteした。既存500問にはroute対象がなかったため、保存済み120/130は維持値として再利用し、新しい表現4件で効果を測った。

| 指標 | 結果 |
|---|---:|
| 新規日付表現の総合成功 | 4/4 |
| Route選択 | 4/4 |
| 期待する日付・分類・表示 | 4/4 |
| 危険な断定の新規発生 | 0件 |

この4/4は対象限定pilotであり、改善後holdout全体の精度とは表現しない。和暦、相対日付、営業日・休日計算も対象外である。

詳細: [Holdout後のrelease gate](../POST_HOLDOUT_TARGETED_RELEASE_GATE.md)

## 4. 図表質問の受入評価

フローチャートや表を含むsealed PDF 4件・質問10件では、抽出schema valid率100%、必要文書取得率100%、回答キー包含率90%、end-to-end成功率70%だった。回答分類精度は70%で事前閾値80%を下回ったため、総合判定は不合格として残した。

詳細: [Visual sealed holdout v2](../VISUAL_HOLDOUT_V2_RESULT.md)

## Phase 2で説明できること

- 「精度」を検索だけでなく、生成・分類・表示を含む総合成功として定義した。
- 最大原因への案が効かなければ、小pilotで止めて費用と退行を抑えた。
- 開発評価とsealed holdoutを分け、未知データで見つかった弱点を開発結果へ混ぜなかった。
- 不合格や未測定の範囲も残し、検証済み以上の性能を主張していない。
