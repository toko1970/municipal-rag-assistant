# 回答分類失敗15件の要因分析

> **Gold訂正後の扱い:** この文書は評価セットv1.0を使った当時の分析記録として保持する。その後、分類を「質問が直接求める命題」で行う規約へ統一し、累計7シナリオを`根拠十分`へ訂正した。モデル改善として数えない。Version Resolver適用済み出力にv1.2 goldを当てた現在値は、総合成功117/130、分類失敗4、回答生成6、検索3、分類ラベル正解121/130である。本文中のQ176・Q301等の旧goldに基づく分析は当時の記録であり、現行判断には使わない。詳細は[`CLASSIFIER_GOLD_CORRECTION.md`](CLASSIFIER_GOLD_CORRECTION.md)を参照する。

## 目的

Retrieved-evidence回帰でproductionの`classification-decision-v1`に残った分類失敗15件を、同じ対策で改善できる要因へ分ける。ここでは実装や追加API呼び出しを行わず、保存済みの質問、取得根拠、生成claims、`missing_conditions`、分類5要因を確認した。

Text 14件の期待ラベルは100シナリオレビューでユーザー承認済みである。Visualの`VD024`も`user_approved`のdevelopment setに含まれる。主原因の割当てはCodexによる初回レビューであり、対策決定時にユーザーと確認する。

## 分析結果

| 類型 | 件数 | ID | 誤り |
|---|---:|---|---|
| 解決済み条件を未解決と判定 | **8** | `Q121`, `Q126`, `Q196`, `Q201`, `Q231`, `Q281`, `Q286`, `Q416` | 根拠十分 → 判断要 |
| 個別・所管判断の見逃し | 4 | `Q046`, `Q086`, `Q301`, `Q316` | 判断要 → 根拠十分 |
| GeneratorとClassifierの不足判定不整合 | 2 | `Q006`, `Q076` | 文書不足 → 根拠十分、表示拒否 |
| 類似事例の適用可否境界 | 1 | `VD024` | 判断要 → 文書不足 |

最大類型8件の内訳は、`version_conflict`の誤検出7件と`requires_case_facts`の誤検出1件である。両者に共通するのは、版や個別条件が入力中に登場したことを、回答時点でも未解決であることと混同した点である。ただし最初の対策は、件数が多く判定条件を狭く定義できる`version_conflict`7件へ限定する方が安全である。

## 1. `version_conflict`の誤検出: 7件

### 観察

- `Q121`, `Q196`, `Q201`, `Q281`, `Q286`: 質問に2025年9月または10月が明記され、claimsも施行日前後の適用関係を解決して正しい結論を返している。
- `Q416`: 旧通知と改正通知の優先関係そのものを質問しており、claimは改正通知を優先すると解決している。
- `Q231`: 住居届の処理順を一つの根拠から回答している。取得集合に他制度・他版が含まれるだけで、回答対象のclaimには競合がない。

分類器は「複数版または異なる記載が取得された」ことと、「質問へ適用する版を決められない」ことを区別できていない。現行契約で`version_conflict=true`にすべきなのは後者だけである。

### 対策候補

`answer-classification-v2`候補として、`version_conflict`を次のように限定する。

1. 競合が質問への結論に関係する。
2. 施行日、基準日、明示された優先規則を使っても適用版を一意に決められない。
3. 版が複数取得された事実だけでは`true`にしない。

負例として年月・施行日で解決できるケース、正例として基準日がなく実際に適用版を決められない`Q176`を与える。保存済みのgenerator出力を固定し、分類器だけを既存v1と候補で比較する。

### 最大改善幅とリスク

この7件だけが改善し退行がなければ、pipeline成功は106/130から113/130へ、81.5%から86.9%へ上がる。これは実測効果ではなく、対象件数から計算した上限である。

主なリスクは、真の版競合まで`根拠十分`へ緩和することにある。最低限、`Q176`を正例controlとして維持し、全130件で`判断要`と`文書不足`の取りこぼしが増えないことを確認する。

## 2. `requires_case_facts`の誤検出: 1件

`Q126`は質問中に「2025年10月」「1.4km」「車通勤」が与えられ、距離要件を満たさないと確定できている。個別事情が話題に含まれることと、結論に必要な個別事情が不足していることを混同した。

これは最大類型と共通原理を持つが、`version_conflict`とは別factorである。最初の候補へ同時に入れると変更要因が二つになり、改善・退行の原因を説明しにくい。version対策の後に「質問とclaimsで必要事実が充足済みなら`requires_case_facts=false`」を独立比較する。

## 3. 個別・所管判断の見逃し: 4件

- `Q046`: 確認先は明記されているが、控除額の正否は個別確認が必要。
- `Q086`: 一括・分割の選択は職員事情による。
- `Q301`: 扶養実態と生計維持関係を総合確認し、所属では即決できない。
- `Q316`: 期限後も受付可能だが、認定・支給時期は個別確認が必要。

claimsは「事情を考慮」「総合確認」「即決できない」「個別確認」と正しく述べたが、classifierは判断要因をすべて`false`にした。分類promptへこれらの意味規則を追加する候補がある。

ただし、確認先を答えるだけで質問が完結するケースまで`判断要`へ広げる危険がある。たとえば「制度解釈が難しい場合の確認先はどこか」という一般手順への回答は、文書だけで確定できる可能性がある。質問が求める結論自体に未解決の個別判断が残るかを判定する必要があり、version対策より境界が複雑である。

## 4. GeneratorとClassifierの不足判定不整合: 2件

`Q006`と`Q076`では、generatorが「別規程が必要」と正しく回答し、`missing_conditions`にも不足文書を入れた。一方classifierは`retrieval_sufficient=true`かつ`answer_fully_supported=true`としたため、`根拠十分`の表示条件に反しvalidatorが回答を拒否した。

`missing_conditions`がある場合に一律で`文書不足`へ変える方法は採用できない。個別事実の不足なら期待ラベルは`判断要`になるためである。根本対策には、少なくとも不足条件を「不足文書」「個別事実」「所管判断」へ構造化するか、不整合時の再分類規則を設計する必要がある。2件に対して変更範囲が広いため、最初の対策には向かない。

## 5. 類似事例の適用可否境界: 1件

`VD024`は出生の記入例を転居にも適用できるかを問う。必要fixtureは取得できたが、転居時の規定は記入例から確定できない。goldは「記入例の直接適用はできず個別確認が必要」として`判断要`、classifierは`retrieval_sufficient=false`として`文書不足`にした。

これはVisual検索失敗ではなく、「関連例はあるが別事由へ適用するには所管判断が必要」という分類境界である。1件だけを狙う規則は過適合しやすいため、同種の正例・負例を追加してから扱う。

## 推奨する次の一手

最初は`version_conflict`7件へ限定する。既存v1と候補promptを、保存済みのretrieved evidence・generator出力に対して同じケース順で各1回比較する。対象7件だけでなく、真の版競合`Q176`、他の正しい`判断要`、`文書不足`をcontrolへ含める。

採用条件は次のとおりとする。

- 対象7件の改善が1件以上ある。
- `Q176`を含む既存正解の`判断要`と`文書不足`を1件も退行させない。
- 改善した候補だけを全130件のretrieved-evidence回帰へ進める。
- 全体で改善0件、または重大ラベルの退行が1件でもあれば不採用とする。

この順序なら「最大原因へ一つだけ対策」「同じ評価条件で比較」「効かなかった変更も保存」というポートフォリオの説明を維持できる。

## 実測後の判断

候補promptは対象7件中5件を最終ラベルまで改善したが、個別事情が必要なcontrol `Q206`と`Q211`を`判断要`から`根拠十分`へ退行させた。採用条件のcontrol退行0件を満たさないため不採用とした。詳細は[`VERSION_CONFLICT_PROMPT_EXPERIMENT.md`](VERSION_CONFLICT_PROMPT_EXPERIMENT.md)を参照する。

7件すべての`version_conflict`自体は解消した一方、2件は`requires_case_facts`へ失敗要因が移り、control 2件では真の`requires_case_facts`が消えた。次の判断では、同一LLMに5要因をまとめて返させたままpromptを追加するか、日付・施行日で解けるversion判定を独立させるかを比較する必要がある。

独立したVersion Resolverの切り出し評価では、修正round後にversion誤検出7/7と真の競合1/1を正しく判定した。factorだけの条件付き合成は17/17だった。ローカルquery flowへfallbackと表示契約検証を含めて統合し、同じ130問の保存済み出力で回帰したところ、分類失敗は15件から9件、成功は106件から112件となり、退行は0件だった。`Q196`は未確認条件が残るため安全にfallbackし、実改善は6件である。詳細は[`VERSION_RESOLVER_EVALUATION.md`](VERSION_RESOLVER_EVALUATION.md)を参照する。
