# 分類改善の本番受入準備：第1候補は採用停止

2026年10月9日。今回の作業では本番を更新していない。既定の分類契約はv1のままであり、新候補は明示設定 `CLASSIFICATION_CONTRACT_VERSION=scope_v2` の場合だけ選択される。

## 結論

`scope-classification-v2-candidate`は独立レビューで表示の安全性に問題が見つかり、既知入力の比較を途中停止した。未知challenge、代表回帰の新規LLM実行、fresh sealed holdoutには進んでいない。前回のプロンプトだけの実験で得た20/20を今回の候補の成績として流用しない。

問題は、版競合を解消する後段処理が、回答内容を再検証せずラベルだけを根拠十分へ変えることだった。たとえば文書から2027年の単価300円を一意に選べても、生成済みの「単価を確定できません」という回答をそのまま十分と表示できた。独立担当がAPIなしで再現した。[独立レビュー](independent_review.md)に元候補の指摘と修正版の確認を区別して記録した。

## 実装した仕組み

質問が直接求める対象を分類器に列挙させ、対象ごとに規則の有無、主張の根拠支持、回答項目の充足、人手確認を別フィールドにした。生成回答の不足条件はそのまま採用せず、根拠と質問に照らして再判定する。コードは未知の参照ID、矛盾した構造、回答不足を検査し、生成の不備を文書不足と混同しない。内部失敗はラベルなし・主張非表示とし、画面も成功通知ではなく警告表示にした。

独立レビュー後の作業版は `scope-classification-v2.1-draft`。版解消後の主張を再検証できない場合は `GENERATION_INCOMPLETE` で安全停止する。これは正しい単価を生成し直す回復機能ではなく、不整合を表示しない保守的な修正であり、回答率への影響は未評価である。Resolverの判断根拠、confidence、参照IDと生出力を成功・fallback・不正出力でも監査できるよう補強した。

この修正版に新しいLLM評価結果はない。採用済みと扱わず、次roundで候補・条件を再固定する。

APIは同じ固定入力、同じモデル `gemini-3.1-flash-lite` で両方式を比較した。入力・schema・ソースhashは[manifest](manifest.json)、保存応答は[records](records.jsonl)、中断状態は[summary](summary.json)にある。中断前の成功数は不均衡な部分集合なので比較成功率・正味改善・汎化効果を主張しない。

C04-formalでは旧方式は根拠十分と未解決条件の矛盾で表示停止、新候補も規則なしと人手確認要求を同時に返したため `REVIEW_WITHOUT_RULE` で安全停止した。安全に停止したことと、期待された文書不足を正しく返したことは別である。

保存9応答の予算管理額は0.021322 USD、中断中の1試行の最大予約を含め0.072381 USD。入力1/出力10 USD/百万tokenという管理仮定であり請求額ではない。中断試行の課金有無・実usageは不明。追加APIは実行していない。

旧候補のhash対象ソースは `frozen_source/` に退避した。現在の作業コードは修正されているため、旧manifestを現行コードの証明に用いない。旧入力・結果は上書きせず残す。

## 本番適用まで残る条件

1. v2.1-draftを次roundの候補として固定し、既知入力と版解決後の経路を再検証する。安全停止が正しい回答まで止める割合も測る。
2. 独立担当が[challenge設計](../../fixtures/scope_release_20261009/DESIGN.md)に沿って問題・正解を作り、分類対象・支持・充足・表示を評価する。
3. 既存130問と開封済み100表現を新旧の検索→生成→分類→表示で新規比較し、ストレージ統合、費用、latency、監査を確認する。
4. 合格した候補だけを固定し、独立担当が管理するfresh holdoutで1回の最終受入を行う。
5. 全条件の合格後に既存のCI/Cloud Run経路でデプロイし、revision・traffic・health・代表質問を確認する。

ユーザーは独立担当への分担と、一般的権限と未照合の個別支給を区別する分類境界を確認済み。同じ確認を取り直す必要はない。今回の停止は承認不足ではなく、事前の安全性採用条件を満たさなかったためである。
