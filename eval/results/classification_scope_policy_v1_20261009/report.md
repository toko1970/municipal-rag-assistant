# 質問範囲・分類規約の明示：固定入力での初期比較

2026年10月9日。候補指示を実装し、旧指示と同じ質問・根拠・生成回答を使って新規API比較した。**既知20表現の分類・表示成功は15/20から20/20、両表現成功のシナリオ数は7/10から10/10へ改善した。退行は0。** 事前に固定したGate 1の進行条件を満たした。

ただし、本番採用や汎化改善の証明ではない。生成不足の表示状態と、一つのfactorに主張支持・回答充足をまとめる限界も確認した。候補を本番経路へ接続せず、実験時のまま保存した。

## 実装した候補

[`classification-scope-policy-v1-candidate`](../../../src/classification_scope_policy.py)は、通常の分類入力の前に次の規約を追加する。

- 原質問の対象を一般規則・権限・確認先、条件付き算定、個別結論として区別する。
- 質問外の実務条件を追加せず、質問内で確認済みの事実を再び不足扱いしない。
- 5つのfactorについて、根拠、支持・充足、不足事実、裁量、版競合の判定条件を明記する。

候補全文は[policy.txt](policy.txt)、方式ごとの完全なpromptは[tasks.json](tasks.json)にある。質問・根拠・生成回答のpayload、出力schema、ラベル決定・表示処理は両方式で同じ。対象を人が指定した値やgoldはモデルに渡さず、分類器が原質問から読む。別の対象抽出モデルは追加していないため、抽出結果そのものの正しさを独立fieldで測った実験ではない。

設計・事前条件は[候補設計](../../../design/CLASSIFICATION_SCOPE_POLICY_CANDIDATE.md)と[manifest](manifest.json)を参照。指示の複数条項をまとめた1候補の効果であり、対象説明だけ・factor定義だけの効果は分離していない。

## 比較条件

開封済みdevelopmentの既存v1分類入力から、曖昧なA01/B01を除く10シナリオ×2表現を固定した。元の生成回答は以前のGemini 3.5 Flash Lite実行結果である。今回は生成や検索を再実行せず、分類器だけをGemini 3.1 Flash Liteで両方式とも新規実行した。過去の別モデルの分類成績をbaselineとして代用していない。

加えて診断4例と、事前固定した4表現の両方式1回追加反復を含め、**56/56 API呼出し、API・schema error 0、retry 0**で終了した。温度0、seed42、出力上限1024token。ケース順を固定seedで並べ替え、旧・候補の先行順を交互にした。初回の失敗を反復の成功で置き換えていない。

今回の作成・実装・意味確認は同じ担当である。独立レビューやユーザー承認済みの新規採用goldとして扱わない。既存goldは変更していない。

## 主結果

| 指標 | 新規実行の旧指示 | 候補 |
|---|---:|---:|
| 既知20表現のラベル一致＋表示処理成功 | 15/20 | 20/20 |
| 両表現が成功したシナリオ | 7/10 | 10/10 |
| 必要な個別確認を残す3シナリオ・6表現 | 6/6 | 6/6 |
| 診断4例の全factor一致 | 2/4 | 4/4 |

シナリオの対応は両方式成功7、候補のみ成功3、旧のみ成功0、両方式失敗0。表現単位では改善5・退行0だった。

| 改善した入力 | 旧指示の問題 | 候補で変わったfactor |
|---|---|---|
| B03標準：承認・終了記録がある当番の時間、期限、提出先 | すでにある情報へ個別確認を要求 | `requires_case_facts: true → false` |
| C01の2表現：照合済みの購入費補填額 | 必要条件が揃っているのに個別確認を要求 | `requires_case_facts: true → false` |
| C04の2表現：別契約に定める実際の自己負担率 | 率の根拠がないのに根拠十分と判定 | `retrieval_sufficient: true → false` |

C04の旧出力は`missing_conditions`と根拠十分ラベルが矛盾し、ローカル表示処理が`DisplayContractError`で停止した。誤った確定回答が実際に画面へ表示された事例として数えない。候補は文書不足の通常表示へ進んだ。

A02言い換えは過去の保存評価では失敗していたが、今回の旧指示も成功した。これを候補の改善数へ加えていない。モデル・実行時点が異なる保存結果との混同を避けた。

## 診断と反復

- D01：明示的裁量を両方式とも保持。
- D02：未解決の版競合を両方式とも保持。旧指示は`policy_judgment`もtrue、候補は版競合だけとして、固定した診断期待に一致した。最終ラベルは両方式とも判断要であり、ラベル改善数に加えない。
- D03：根拠と矛盾する金額claimを両方式とも検出。
- D04：提出先への未回答を旧指示は支持済みとし、候補は`answer_fully_supported=false`として検出した。候補ではこのfactorに回答充足も要求している。旧factorの狭い「主張が支持されるか」だけの語義との違いを、同じ正解規約下の通常ラベル精度改善と混同しない。

事前固定したA02言い換え・A03標準・A04標準・C01標準の反復では、両方式とも各4対すべてでfactorが一致した。候補は4表現の両回すべて成功。旧指示はC01の過剰保留も再現した。4表現×1追加反復の結果であり、一般的な決定性の保証ではない。

## 正解ラベルの裏に残る問題

**今回の候補は、Rubric v2を完全に実装したものではない。**

1. D03/D04は根拠がある生成失敗だが、既存v1決定表へfactorを入れると文書不足になる。診断ではfactorの検出を成功と数え、文書不足ラベルを正解にしていない。アプリへ適用する前に`GENERATION_INCOMPLETE`等の状態へ分離する必要がある。
2. 文書不足の6表現では候補も`answer_fully_supported=true`だった。A04標準・B04言い換えはclaimsが空である。`retrieval_sufficient=false`のため最終ラベルは正しいが、「支持」「全要求への充足」「claimなし」を一つのbooleanへまとめた指示は完全には守られていない。既知20表現の全factorを事前goldで採点したわけではなく、20/20を規約全項目への準拠率と呼ばない。
3. 曖昧な条件付き算定A01を除外したため、条件付き算定と実際の支給確定の区別をこの結果だけで十分に検証できていない。

1と2は、次の実装で主張支持と回答充足を別項目にし、生成失敗を通常分類に混ぜない必要性を示す。今回の出力を見て候補や正解条件は変更していない。事前Gate 1の合格と、追加の意味監査で分かった課題を併記する。

## 判断と次の段階

**質問範囲と規約をモデルへ渡す方向は、この固定入力比較では有望であり、開発を継続する。今回の候補をそのまま本番採用する段階ではない。**

次の候補では、対象・根拠支持・回答充足・未確認事項を観察可能な形へ分け、生成失敗の表示契約と接続する。その際、過去のQuestion Contract v2を丸ごと再採用せず、対象抽出の誤りを新しい負担として測る。今回の既知入力は引き続き開発用とし、条件付き算定／個別確定を明確にした新しい対照、質問外条件、例外・複合質問、未知制度を含むchallengeを別に固定する。

採用goldの難しい境界は[採用判定プロトコル9.2](../../INTERVENTION_ADOPTION_PROTOCOL.md)に従ってユーザーと確認する。次の独立評価・代表回帰・安全性gateを通過した候補だけをfresh holdoutへ送る。今回の20/20だけでこの手順を省略しない。
