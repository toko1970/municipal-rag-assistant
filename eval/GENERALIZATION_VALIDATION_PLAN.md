# 回答改善の汎化性能を確認する方針

更新日：2026年10月9日

期限の具体化、分類の意味の明確化、根拠支持と個別判断の分離について、既知の失敗への適合と未知の問題への改善を区別して評価する。改善候補を固定し、開発に使っていないシナリオで旧方式と比較することを基本とする。本書はセッション間の引継ぎ資料であり、汎化検証の完了や改善の本番採用を示すものではない。

## 既存方針との関係

採用手順は[改善策の採用判定プロトコル](INTERVENTION_ADOPTION_PROTOCOL.md)を参照する。本書は今回の原因検証を受けた具体的な評価対象を補足し、既存の採用条件を置き換えない。分類候補の語義と決定順序は[分類 Rubric v2](../design/CLASSIFICATION_RUBRIC_V2.md)を確認する。過去のv1正解を事後変更せず、新しい分類規約による評価とは別に報告する。

## 検証済みの出発点

[結果レポート](results/failure_hypotheses_verification_20261009/report.md)と[独立した最終レビュー](results/failure_hypotheses_verification_20261009/review_round2.md)に記録した探索的検証では、次を確認した。

| 対象 | 観測結果 | 汎化確認に残る課題 |
|---|---|---|
| 期限の具体化 | 今回の旧指示は1/4。具体年月日時の要求、計算許可、期限単問化は各4/4 | 2シナリオの各2表現に限定。どの介入が主因かは未特定 |
| 分類指示の明確化 | 元4例の旧正解ラベル一致が0/4から2/4 | 正解規約の境界を含め、指示追加だけでは解決しない |
| 根拠支持と個別判断の2軸化 | 元4例すべてで事前期待と一致 | 判定対象は担当が指定。質問からの対象抽出と最終表示は未検証 |
| 表示契約 | 異常2分岐と正常対照の3条件を再現 | 元の実行失敗2件の発生分岐は保存記録から特定不能。回復策の効果は未検証 |

元100表現は保存採点の再集計であり、現行アプリ100表現の新規回帰ではない。新規APIは有効37応答、入力不備で無効化した2応答を含め39呼出し。検証担当とレビュー担当を分け、レビューに伴う再検証を2回実施して終了した。この2回の上限は完了済みの原因検証に対する指定であり、次の実験回数は実行前に別途固定する。

## 確認する汎化の範囲

| 評価 | 確認すること | 設計例 |
|---|---|---|
| 同じ制度の未使用シナリオ | 未知の条件の組合せへの対応 | 新しい日付、不足条件、複合質問 |
| 制度ごと分けた評価 | 特定の文書や制度への依存 | 開発に使わない架空制度を用意し、評価時は文書を検索可能にする |
| 条件を一つ変える対照 | 結論を変えるべき条件の識別 | 照合済みと未照合、基準日の前後 |
| 意味を保つ変更 | 表現や不要情報への耐性 | 口語、日付表記、語順、無関係な根拠、根拠の提示順 |
| 一連の処理を通す評価 | 部品の改善が最終回答へ届くか | 検索、生成、分類、表示まで実行 |

同じシナリオの標準表現と言い換えは同じ評価群に置く。制度をまたぐ汎化を測る場合は、同じ制度・文書系列を開発用と最終評価用にまたがらせない。名称だけ置き換えた同型テンプレートを独立した未知制度の証拠として扱わない。

## 改善ごとの重点項目

期限は月末、年末、うるう年、前後の日数、時刻指定、複数期限を含める。日付や起算規則が不足する場合には具体日を作らないことも確認する。営業日・休日を扱う場合は、根拠とカレンダーの有無、対応範囲を事前に定義する。

分類は、根拠があり条件も揃う場合、根拠はあるが個別可否が未確定の場合、根拠自体がない場合を区別する。2軸化では、質問から判定対象を自動抽出する処理、各軸の判断、最終表示を分けて採点する。「保留と答えられる」ことを「給付可否が確定する」ことと混同しない。

表示失敗への対策は、異常から適切に回復することと、正常な回答を誤って止めないことを測る。根拠のない断定への置換を回復成功と数えない。この項目は汎化だけでなく信頼性の評価として扱う。

## 実施手順

1. 改善候補、変更箇所、分類規約、必須回答項目、主指標、採用条件、モデル設定、反復数、費用・呼出し・再試行上限を事前に固定する。複数候補の探索と最終採用の評価を分ける。
2. 評価作成・レビュー担当と改善担当を分ける。最終評価の質問・正解は改善担当に見せず、正解側の不足条件をモデル入力に混ぜない。分類境界など難しい正解は既存プロトコルに従ってユーザーと確認する。
3. 開発用の未知同型ケースで候補を選び、既存100表現を含む回帰対象を新規実行する。保存結果の再集計とは区別する。既存130問回帰など、既存プロトコルの受入条件も維持する。
4. まず根拠・入力を固定して改善部分だけを比較し、その後に検索から表示まで実行する。旧方式と候補を同じ問題・モデル設定で比較し、単独変更の効果を確認してから組み合わせる。
5. 出力の揺らぎは両方式で同じ回数を実行して測る。反復対象は結果を見る前に固定し、良い応答だけを選ばない。温度0を決定性の保証とみなさない。
6. 候補固定後、独立した最終評価を実行する。採点担当には可能な範囲で方式名を伏せる。日付の年省略などの意味判定も確認し、自動採点値とレビューによる訂正を別記する。
7. 最終評価を見て修正した場合、その評価セットは開発用に移す。次の汎化確認には新しい最終評価セットを用いる。

## 指標と判断

総合回答成功率だけでなく、両方式成功、旧方式のみ成功、候補のみ成功、両方式失敗を記録する。改善数と退行数を示し、誤った支給確定、不要な確認要求、根拠外の主張、期限誤り、回答なしを別々に集計する。費用と処理時間も比較する。

根拠支持と個別判断の正しさ、対象抽出、回答項目の網羅性を別に測る。分類規約を変更した効果と、同じ規約の下での精度改善を混ぜない。

不確実性はシナリオ単位で扱い、言い換えや反復を独立標本として水増ししない。制度単位の評価なら制度間のばらつきも示す。弱点を多く含む試験の正答率を実利用全体の成功率と呼ばず、想定質問分布に基づく評価と区別する。

初期規模の案は新規40〜60シナリオ、各2表現。これは必要十分な件数でも確定済みの実行計画でもない。開発用と最終評価用の配分、検出したい差、制度数、費用に応じて実行前に決める。少数例で差が不明なら、改善や同等性を断定しない。

## 次のセッションの開始点
