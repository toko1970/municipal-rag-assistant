# 分類改善の本番受入計画（2026-10-09）

ユーザーの依頼に基づき、scope policy初期比較の後続を進める。前回の20/20は既知固定入力の成績であり、今回の候補の採用根拠として代用しない。

## 今回の候補

候補名は`scope-classification-v2-candidate`。分類器1回の出力で質問対象ごとに根拠の有無、主張支持、回答充足、人手確認を別々に返す。生成schema・検索・期限計算は維持し、質問を分解する追加LLM callは作らない。最終表示はコードが決定し、生成不備とprovider/schema不備はラベルなし・claim非表示の内部失敗にする。候補は明示的な設定で選べるようにするが、採用gate以前に既定値・公開環境を変えない。

文書不足は規則欠如、生成不足は規則があるのに主張が不支持または回答項目欠落の場合である。内部に両方がある場合は全診断を保存し、通常の表示ラベルはRubric v2の順序に従う。Generatorの不足条件をそのまま最終確認事項として信用せず、分類器が対象ごとに根拠とともに再判定する。

## Gateと事前上限

各段階は前段に合格した場合だけ実行する。主候補は1つ。結果を見たprompt修正は別roundとし、同じholdoutを再利用しない。

| 段階 | 条件 | API試行上限・管理費用上限 |
|---|---|---|
| 1: 契約・既知入力 | 正常と異常のローカルテスト、前回24入力の両方式比較、既知20表現で正味改善、新規退行0、生成不備診断の安全停止 | 56回・0.80 USD |
| 2: 未使用challenge | 別担当が作成・固定する文書系列、一般規則/個別可否/文書不足/生成不足/複合/版。対象抽出・意味判定・最終表示を評価し、候補正味改善、新規危険断定0、表現対の退行0 | 240回・4 USD |
| 3: 回帰 | 既存130問と開封済み100表現を新規paired実行。総合正味改善、危険断定と根拠外主張の新規退行0。保存結果再集計は代替にならない | 1,500回・25 USD |
| 4: 運用 | schema/provider/未知ID/回答欠落で安全表示。費用・latency記録。追加分類APIは1回まで、通常時の呼出し数は増やさない | ローカル試験はAPI 0 |
| 5: fresh holdout | 0〜4の候補を固定後に未開封の新規評価を1回だけ実行。両方式同じ入力で採点、総合正味改善、危険側退行0、独立意味レビュー。問題・goldの作成と改善担当を分離 | 400回・7 USD |

合計上限2,196 API試行・管理費用36.80 USD。入力1/出力10 USD（百万tokenあたり）の保守的な予算管理仮定であり、公式料金・請求額ではない。各API前に入力byte数と最大出力で予約し、上限到達で停止する。API開始間隔は12.2秒以上、timeout45秒、SDK retry1試行、実験retry0。provider障害があればそのrunは停止して記録し、モデルを勝手に切り替えない。段階ごとの入力数・モデル・出力上限・採点条件はAPI前のmanifestでさらに固定する。

最初の契約変更は旧方式の分類ラベルを生成失敗へ置き換えるため、旧goldと新契約の成功条件を分ける。診断用の不完全回答を「文書不足の正解」とは数えない。対象が曖昧な採用goldはユーザーと確認し、事後に書き換えない。

## 本番への経路

現行のCloud Run/既存GitHub Actions経路を利用する。既存runbookのPR番号や過去revisionは参考であり、今回の対象として流用しない。採用条件を満たしたcommit、CI、承認を要する実際のenvironment gate、image、revision、traffic、health、代表質問を確認して完了とする。明示的な承認gateを迂回しない。候補が不合格の場合はデプロイせず、不合格の証拠と次の作業を保存する。

## ユーザー確認（2026-10-09）

独立した評価作成・レビューへのエージェント分担を承認済み。分類境界も次のように確認済み：文書が所属単独の決定を禁止し記録照合を要求する場合、一般的な権限を聞く「所属だけで決められる？」は根拠十分。記録未照合の特定職員について支給額確定を求める質問は判断要とする。後者で「確定できない」と説明できることだけを根拠十分の理由にしない。

## 今回roundの終了状態

元候補は独立レビューの安全性不備で採用停止。APIは10試行開始・9応答保存で中断し、後続gateは未実施。旧ソースを保存した上でv2.1-draftへ安全修正し、関連73テストと独立レビューを通過した。新draftのAPI評価・holdout・本番適用は未実施。結果は[受入準備レポート](../eval/results/scope_release_gate1_20261009/report.md)を参照。次roundでは修正版・採点・予算を再固定し、旧roundを完走済みとして扱わない。

## v2.2の不具合対応（2026-10-09、別round）

版競合解消後の一律停止を、生成済み回答の再検証へ置き換える。元の質問・取得根拠全文・生成回答・元targets・版解決観測を分類器へ渡し、元の対象/intent/claim対応を維持する。個別事実と裁量のreviewはコードでも保持する。支持・充足の失敗、低confidence、版判定の不一致、対象変更、不正参照、provider失敗ではラベルなし・claim非表示とする。

通常経路の追加callは0、版解消時だけ追加分類callを1回まで認める。生成し直し・アプリ側の再試行・循環呼出しはしない。再検証の入出力、実際に採用した判定、費用用tokenとエラーを同一request IDで記録する。以前の「通常時の呼出し数は増やさない」は維持し、版解消時の追加費用・latencyは今後の全経路評価に含める。

既知不具合のsmall probeを4条件×1回で実施する。正しい単価、解消済み競合を理由にした不完全回答、旧単価の誤答、個別確認保持を用いる。試行上限4、管理費用0.40 USD、間隔12.2秒、timeout45秒、retry0、最大出力4096、温度0/seed42。実行前manifestでモデル・ソースhash・入力・正解条件を固定する。単なるschema/API失敗を正しい不完全回答検出に数えない。これは開発用の部品検証で、Gate 1全体・回帰・holdoutを代替しない。キャンペーン全体の既存予算上限内で管理する。
