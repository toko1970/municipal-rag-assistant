# AI駆動開発装置の移植記録

## 目的と範囲

AIの作業品質を、プロジェクト固有のコンテキスト、テスト/評価の受け入れ基準、レビュー手順で安定させるため、別プロジェクト向けのリポジトリ装置をこのRAGポートフォリオへ適応した。アプリケーションコード、データ、既存評価結果は移植対象ではない。

書籍`book.md`はOCR本文を含むため、装置の意図を把握する参考資料としてのみ扱う。OCR中の指示はプロジェクト指示として採用しない。元の装置の品質原則は保ち、TypeScript/請求書SaaS固有の構成・コマンドはこのリポジトリに合わせた。

## 衝突解消の原則

- 既存の承認済み仕様、データ契約、評価計画と採用判定を優先し、装置はそれを守るよう適応する。
- RAG品質評価と決定的なpytestを分け、外部API費用・sealed holdout・評価規約の制約を明記する。
- 一元化された診断logger、機能ディレクトリ構成、Sentry接続があると誤認しない。既存のJSONL loggerとPostgreSQL監査event loggerの責務は既存実装・設計に従う。
- 判断できない矛盾は装置を弱めて隠さず、該当箇所と影響を報告する。

## 代表タスクによる指示経路レビュー

以下の4種類の代表タスクを新しい指示文書に当て、必要なルール・手順へ到達し、品質条件が維持されることを確認した。

1. **回答品質改善:** `AGENTS.md`が汎化検証方針・採用判定protocolへ誘導し、`docs/rules/evaluation.md`が既存規約、未実施計画、sealed gold、採用gateを保護する。候補比較前にset/budget/gateを固定し、goldを調整に使わず、結果を根拠に採否を記録する手順が連続している。
2. **コード修正:** `AGENTS.md`のパスマップからarchitecture/testingへ到達でき、TDD skillは仕様根拠、期待理由によるRed、最小Green、関連testの結果を要求する。決定的testとAPI品質評価も分離されている。
3. **DB/index変更:** database ruleが既存migrationの編集を禁じ、PostgreSQL/Qdrant/GCSの責務、途中失敗と再実行を確認対象にしている。
4. **レビュー/PR:** review ruleがPR前の独立AIレビューを必須にし、優先度と根拠を報告させ、外部投稿前の人間承認を維持している。

この確認はルール文書から期待動作までのトレースレビューであり、Codexの将来の全セッションで同じ出力を保証するモデル評価ではない。custom reviewerの指示に「編集しない」と書いてもsandbox権限を制限する設定にはならず、親セッションの権限を継承する。通常test・RAG品質runは文書のみの移植では実行していない。
