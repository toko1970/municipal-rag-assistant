# 学習・Codex利用枠運用計画

## 1. 目的

RAGを完成させるだけでなく、ユーザーが設計判断、実装、検証結果を自分の言葉で説明できる状態を作る。同時に、ChatGPT Plusの5時間枠と週間枠を使い切って工程の途中で再現情報を失わないようにする。

使用量はモデル、推論量、taskの複雑さ、tool利用などで変わるため、固定のメッセージ数では見積もらない。CodexのUsage画面または利用可能なusage取得機能に表示される使用率とreset時刻を工程開始時の判断材料にする。

## 2. 一つの学習単位

各Phaseをさらに次の単位へ分割する。

1. **学習目標**: 完了後に説明できる概念を1〜3個に絞る。
2. **現状確認**: 関係するコード、データ、test、制約を読む。
3. **設計比較**: 採用案と最低1つの代替案を比べる。
4. **最小実装**: 一つの検証可能な変更だけを入れる。
5. **検証**: 成功例だけでなく、境界条件または失敗時動作を確認する。
6. **振り返り**: 変更理由、処理の流れ、結果、限界、次の課題を記録する。

各単位の完了時には次を提示する。

- 変更ファイル
- 学んだ概念
- 実行したコマンドとその目的
- 検証結果
- 面接で説明できる要点
- 次の学習単位

## 3. 利用枠による作業モード

2026-09-27から短期集中期間はPro planを利用している。利用状況取得では5時間枠ではなく週間枠だけが表示される場合がある。その場合も、表示された利用枠をその時点の正として下表の割合を適用する。reset creditは引き続き明示的な確認なしに使用しない。

| 使用率 | モード | 実施する作業 |
|---:|---|---|
| 0〜59% | 通常 | 一つの学習単位を設計から検証まで進める |
| 60〜79% | 節約 | 読み取りとtool callをまとめ、現在の単位を完了させる |
| 80〜89% | checkpoint | 新しい大規模作業を始めず、局所編集、検証、説明、再開情報を残す |
| 90%以上 | 停止準備 | 追加実装を止め、未完了作業と再開手順を保存する |

5時間枠と週間枠のどちらか高い方を作業モードの判定に使う。reset後はUsageを再確認してから通常作業へ戻す。

## 4. Loopとreview

- loop開始前に、対象artifact、期待する成果、最大round、停止条件を宣言する。
- reviewerは異なる観点が必要な場合だけ使い、同じ確認を無制限に繰り返さない。
- 各roundで未解決事項、修正証拠、次roundの対象をローカル記録へ残す。
- 使用率80%以上では新しいloopを開始しない。進行中loopは重大事項の記録と終了判定を優先する。

## 5. 中断・再開checkpoint

利用枠または外部API制限で中断するときは、少なくとも次を残す。

```text
目的:
完了:
未完了:
変更ファイル:
実行済み検証:
失敗・注意点:
次に実行する最小コマンド:
```

checkpointは秘密情報を含めず、作業内容に応じて設計資料、評価report、またはtaskの引継ぎ情報へ保存する。

## 6. Phase 0への適用

Phase 0は次の学習単位へ分ける。

1. fixtureとgold annotationの役割、development / holdout分離を学ぶ。
2. 一種類の図表だけでfixture、annotation、schema validationを縦に通す。
3. 残り5種類へ同じ仕組みを拡張する。
4. 50シナリオをfamily単位で分割し、manifestを固定する。
5. Cloud SQL、GCS、Qdrant Cloud、Geminiの接続・費用spikeをサービスごとに行う。

最初の実装対象は「申請処理フローチャート1件のfixtureとgold annotation」とする。ここでPDF座標、JSON Schema、flow node・edge、holdout leakageの基礎を確認してから対象を広げる。
