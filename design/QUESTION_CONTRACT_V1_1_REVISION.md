# Question Contract v1.1 再設計

- 作成日: 2026-09-30
- 状態: Gate B1不合格（意味上15/18）。アプリケーションへ未統合
- 比較対象: `question-contract-v1`
- 評価セット: v1と同じ開封済み18件（sealed holdoutは使用しない）

## 1. なぜ見直すか

v1はGate B1で完了12件中6件だけが意味上正しかった。失敗は個別質問の語句ではなく、次の三つの構造上の曖昧さへ集約できる。

| 原因 | 事例 | v1の不足 |
|---|---|---|
| 質問要求の書換え・追加 | TH025 2件、TH031 | `requirement`を自由文で生成でき、質問のどの部分に対応するか検証できない |
| 複数対象の統合 | TH034 noisy | 同じ回答種類を対象別に分ける規則と、対象を示す構造がない |
| 明示された入力事実の脱落 | TH034 formal、TH047 formal | `text`が質問の原文か、モデルの推測・言換えかを検証できない |

503で未実行だったcontrolは品質失敗へ数えていない。しかし、上記6件が確定した時点で18/18という事前gateは達成不能だったため、v1は不合格とした。

## 2. v1.1の一般ルール

v1.1は特定の制度名や日付を条件分岐へ追加しない。すべての質問へ次を適用する。

1. facetは質問者が明示的に回答を求めた原文`request_quote`を持つ。
2. `request_quote`は元質問の連続部分文字列でなければコードが拒否する。
3. 回答種類は制度上の意味ではなく、`yes_no`、`amount`、`date_or_time`、`list`、`explanation`、`other`という回答の形に限定する。
4. 対象ごとに答えが変わり得る場合はfacetを分け、質問原文の`scope_quotes`で対象を区別する。
5. 入力事実は元質問からコピーした`source_quote`を持ち、質問にない記述をコードが拒否する。
6. 同一の要求・回答形・対象を持つ重複facetをコードが拒否する。

## 3. v1から変えた理由

| v1 | v1.1 | 狙い |
|---|---|---|
| 自由文`requirement` | 原文`request_quote` | 質問にない要求の創作を観測・拒否する |
| `eligibility`、`procedure`、`authority`等 | 回答形6種 | 重なる意味カテゴリ間の迷いを減らす |
| 対象を`requirement`へ埋込 | `scope_quotes` | 複数日・複数対象を分けた根拠を明示する |
| 自由文`text` | 原文`source_quote` | 入力事実の出所を監査できるようにする |

原文引用だけでは「質問の全事実を漏れなく抽出した」とコードで証明できない。完全性は同じ18件の期待値と未知challengeで測る。v1.1が保証するのは、出力した要求・事実が少なくとも質問に実在することと、複数対象を独立表現できることである。

## 4. 採否手順

1. Schema、原文参照、ID、重複のunit testを外部APIなしで通す。
2. v1と同じ18件を最大18 logical calls、retry 0、US$0.05以下で実行する。
3. provider errorは品質不正解と分けてfail-fastする。
4. 自動採点後、全完了ケースを意味レビューする。
5. **18/18のときだけ**B2へ進む。未達なら、失敗機構を記録して候補の再修正または棄却を判断する。

v1.1の例示は評価質問と異なる架空例を使う。既知18件の正解文をpromptへ埋め込まず、評価セットへの直接的な過適合を避ける。

## 5. 代替案

| 案 | 判断 |
|---|---|
| v1 promptへ6件の正解例を追加 | 既知質問への過適合が強いため不採用 |
| キーワードごとのfacet分割 | 制度語・表現の追加に伴い規則が増えるため不採用 |
| 質問全文を節へ完全分割 | 完全性は上がるが、境界規則と出力が過度に複雑になるため今回は不採用 |
| 原文引用付きfacetと事実 | 小さい変更で創作を拒否し、失敗機構を観測できるため採用候補 |
