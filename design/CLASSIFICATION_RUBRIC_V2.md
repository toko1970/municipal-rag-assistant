# 回答分類Rubric v2

- version: `classification-rubric-v2.0`
- 確定日: 2026-09-30
- 対象: オンライン回答分類、development評価、今後作成するholdout gold
- 旧仕様との関係: v1の過去結果は変更せず、v2以降の実装と評価へ適用する

## 1. 分類の目的

回答分類は、質問内の状況だけから決めない。質問が求める命題、今回取得した文書、生成回答の関係を確認し、利用者が回答をどのように扱うべきかを示す。

本ポートフォリオでは、制度所管部署に確認した場合も同じ回答になることの証明と、corpus全体に適用可能な規則が存在しないことのオンライン証明を完成条件にしない。

## 2. 三つの表示分類

### 2.1 根拠十分

次をすべて満たす場合である。

1. 質問が直接求める全項目について、今回取得した文書に適用可能な規則がある。
2. 生成回答の全重要claimが、取得文書、質問から与えられた入力値、検証済み計算で支持される。
3. 質問が求める項目をすべて回答している。
4. 結論を変える未確認の個別事実、明示的な制度裁量、未解決の版競合が残らない。

文書の文言をそのまま返す場合だけでなく、文書の計算式、閾値、日付規則を質問の入力へ機械的に適用して結論が一つに決まる場合も含む。

### 2.2 判断要

次をすべて満たす場合である。

1. 今回取得した文書に、質問の結論へ関係する判断基準または確認手順がある。
2. その基準に沿った説明claimは文書に支持される。
3. 最終結論を一つに決めるために、次のいずれかが残る。
   - `case_fact`: 結論を変える個別事実の確認
   - `policy_judgment`: 文書が明示的に残す裁量または複数の正当な解釈
   - `version_conflict`: 必要な基準日等が揃っても解消しない適用版の競合

文書に「所管部署へ確認」と書かれているだけでは、すべての質問を`判断要`にしない。質問が「確認先はどこか」「所属だけで決められるか」を尋ね、文書からその命題へ一意に答えられる場合は`根拠十分`である。

### 2.3 文書不足

質問が直接求める少なくとも一つの項目について、今回取得した文書に適用可能な規則または判断基準がなく、類似制度からの転用や一般論による推測なしには答えられない場合である。

オンライン表示は「今回取得した根拠では回答を確認できませんでした」とする。corpus全体に規則が存在しないとは断定しない。

評価時にだけ、review済みgoldの`expected_corpus_answerability`を使い、検索失敗とcorpus非掲載を分離する。

## 3. 表示分類へ含めない内部失敗

### 3.1 GENERATION_INCOMPLETE

今回取得した文書には必要な規則があるが、Generatorが次のいずれかになった場合である。

- 質問が求めるfacetのclaimを作らなかった。
- claimが取得文書や検証済み計算に支持されない。
- 一部facetだけを回答した。

利用者へ不完全な分類付き回答を表示しない。評価では回答生成失敗として記録し、`文書不足`や分類失敗へ混ぜない。

### 3.2 PIPELINE_INCONSISTENCY

Schema違反、未知ID参照、facet欠落、分類と構造化回答の矛盾がある場合である。分類付き回答を表示せず、pipeline failureとして記録する。

### 3.3 PROVIDER_ERROR

429、503、timeout等で処理が完了しなかった場合である。品質不正解と分けて可用性へ記録する。

## 4. 分類器が返す観察値

分類器へ最終ラベルを返させない。requested facetごとに次を返させる。

### 4.1 evidence_coverage

| 値 | 定義 |
|---|---|
| `sufficient` | 今回取得した文書に、そのfacetへ答える規則または判断基準がある |
| `insufficient` | 今回取得した文書だけでは、そのfacetへ答える規則または判断基準を確認できない |

### 4.2 claim_support

| 値 | 定義 |
|---|---|
| `fully_supported` | facetへ答える全重要claimが取得文書、入力値、検証済み計算で支持される |
| `partially_supported` | 一部claimだけが支持される |
| `unsupported` | claimが取得根拠と矛盾する、または根拠から導けない |
| `no_claim` | facetへ答えるclaimがない |

### 4.3 human_review_requirements

| type | trueにする条件 | trueにしない例 |
|---|---|---|
| `case_fact` | 文書の判断基準はあるが、結論を変える具体的事実が質問にも取得根拠にもない | 質問へ必要な日付・金額・状態がすべて書かれている |
| `policy_judgment` | 必要事実が揃っても、文書が明示的裁量または複数の正当な解釈を残す | 閾値、計算式、明示的flowを適用するだけ |
| `version_conflict` | 必要な基準日等が揃っても、取得文書から適用版を一意に選べない | 基準日で旧版・新版を一意に選べる |

各requirementは対象facet、説明、根拠IDを持つ。一般的に別事情があり得るという理由だけで追加しない。

## 5. コードの決定表

全requested facetを評価した後、上から順に適用する。

| 優先 | 条件 | 結果 |
|---:|---|---|
| 1 | Schema、ID参照、facet完全性が不正 | `PIPELINE_INCONSISTENCY` |
| 2 | いずれかのfacetが`evidence_coverage=insufficient` | `文書不足` |
| 3 | evidenceは十分だが、いずれかのfacetが`fully_supported`でない | `GENERATION_INCOMPLETE` |
| 4 | 全facetがfully supportedで、human review requirementが1件以上 | `判断要` |
| 5 | 全facetがfully supportedで、human review requirementが0件 | `根拠十分` |

`文書不足`とhuman review requirementが同時に返った場合は、分類出力自体の意味整合性を確認する。文書に判断の土台がないfacetへ、根拠のないhuman review requirementを追加してはいけない。複数facet質問で、あるfacetが文書不足、別facetが判断要なら、表示分類は`文書不足`としてclaimを表示せず、内部ログには両facetの診断を残す。

## 6. 質問範囲による境界

分類対象は「質問が直接求める命題」である。

| 質問 | 文書の記載 | 分類 |
|---|---|---|
| 確認先はどこか | 人事給与課へ確認と明記 | 根拠十分 |
| この職員へ支給できるか | 個別記録を照合して決定と明記。記録未確認 | 判断要 |
| この規程だけで割合を確定できるか | 別規程によると明記 | 根拠十分 |
| 実際の割合はいくらか | 別規程を取得できていない | 文書不足 |
| 条件を満たす場合の金額は | 単価・上限・適用日が一意 | 根拠十分 |
| この案件の金額は | 上限を選ぶ基準日が不明 | 判断要 |

## 7. 質問入力と文書根拠

質問に書かれた日付、金額、状態は、制度文書の代わりになる根拠ではない。文書規則へ適用する入力値として扱う。

```text
question input + retrieved document rule + verified calculation = derived claim
```

Question Contractはrequested facetとinput factを識別するが、input factの存在から最終分類を直接決めない。分類器は生成claimの導出経路と、結論を変える不足条件が本当に残るかを評価する。

## 8. 評価上の扱い

- rubric変更によるgold訂正は精度改善として数えない。
- 過去のgoldと結果artifactは変更せず、rubric versionを付けた新しいannotationを作る。
- oracle evidence評価とretrieved evidence評価を分ける。
- `GENERATION_INCOMPLETE`、`PIPELINE_INCONSISTENCY`、provider errorを分類不正解へ合算せず、総合回答成功ではすべて失敗として扱う。
- 複数表現を持つ同一scenarioは同じ期待分類とし、表現安定性を別に測る。

## 9. 現行ラベルとの互換性

初期実装では履歴比較のため、内部・評価ラベルを`根拠十分`、`判断要`、`文書不足`のまま維持する。利用者向けの`確認が必要`、`根拠不足`への表示名変更は、判定ロジックの効果と分けて候補採用後に行う。
