# CI/CDと公開手順

## GitHub Actionsでの検証

CIは次の3つのタイミングで同じ検査を行います。

- **作業ブランチへのpush**で、変更を検証し、PRを出す前から不具合に気づけるようにします。
- **PRの作成・更新**で、変更をマージ先に仮に取り込み、既存コードと組み合わせても動くか確認します。
- **マージによる`main`へのpush**で、候補版を作る前に、実際に`main`に入ったコミットを検証します。

| 検査 | 確認すること |
|---|---|
| Python（Ruff / pytest） | Lintでコード上の問題を検出し、外部APIを使わずにアプリの処理をテスト |
| フロントエンド（Vitest / TypeScript / ESLint / Vite） | 画面の動作、型、Lint、本番用ビルドを確認 |
| 統合テスト（pytest） | テスト用のPostgreSQL・Qdrantを起動し、アプリとの連携を確認 |
| コンテナ起動確認（Docker） | 本番用イメージをビルドして起動し、画面のHTMLとAPIのヘルスチェック応答を確認 |
| インフラ設定（Terraform） | `fmt -check`と`validate`で書式と設定の妥当性を確認 |

## Cloud Runでの候補確認と公開

同じCloud Runサービスに**候補リビジョン**を追加します。リビジョンはコンテナイメージと実行設定を固定した版で、実行インスタンスの数はアクセスに応じて変わります。候補版と現行版はデータベースや検索インデックスを共有します。

候補版への本番トラフィックが0%でも、候補版を作成する前に共有のPostgreSQLへDBマイグレーションを適用します。このため、候補版のデプロイには本番切替とは別に、GitHubの `production` 環境で所有者の承認が必要です。

Cloud Runの標準機能である**トラフィックタグ**を候補リビジョンに付けると、専用の確認用URLが発行されます。候補版への本番トラフィックが0%でも、そのURLから候補版に直接アクセスできます。

GitHub Actionsは候補版のデプロイ直後と本番切替の直前に、確認用URLへ `curl` でアクセスして次の3点を検査します。

- `/` で画面のHTMLを取得し、Reactの描画先 `id="root"` があることを確認します。
- `/api/health/live` でAPIが応答することを確認します。
- `/api/health/ready` でPostgreSQLとQdrantへの接続を確認します。

担当者が候補版の回答・画面を5件レビューし、全件の合格を記録して公開ワークフローを起動します。GitHub Actionsはレビュー結果と候補版の稼働を確認してから本番トラフィックを切り替え、本番URLで同じ稼働検査を行います。

切替後の検査に失敗すると、ワークフローは切替前のトラフィック配分への復旧を試みます。適用済みのDBマイグレーションはそのまま残ります。
